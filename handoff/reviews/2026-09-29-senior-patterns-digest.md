Source: reading material Julian shared (community threads, vendor and practitioner articles on file vs table formats, Iceberg / Delta / Hudi, SCD types in Fabric, Spark tuning). Summarised in our own words as **reasoning patterns**, not facts to copy; ARCHCAT1 turns them into `arch.decision.v1` entries, ARCHLINT1 into detectors. Treat vendor claims (benchmarks, "best format") as biased; keep the *questions*, not the verdicts.

## 1. The meta-rule
Every technology choice has a *why*; without context (volume, writers, engines, freshness, skills, business questions) there is no right answer ("how do I build a bridge that does not fall?"). DataPass always shows: **context → question → options → consequences → choice → what to watch**. Tools (Iceberg, Parquet, polars, DuckDB) are not modelling: dumping data into a good format without thinking about how the business uses it adds little.

## 2. Storage: file format vs table format (two layers, not two choices)
- Parquet / ORC / Avro = how one file stores rows (columnar for scans, Avro row-oriented for write-heavy streams). Iceberg / Delta / Hudi = how many files become one table (atomic commits, schema evolution, time travel, row-level changes).
- Plain Parquet is a complete answer for write-once-read-whole data (exports, archives, ML feature files): no catalog, no maintenance. A table format is needed as soon as there are concurrent writers, updates/deletes, safe schema change or reproducible history.
- Choosing a table format: follow the **primary engine** (Databricks → Delta, optionally UniForm for Iceberg readers; Snowflake / BigQuery → Iceberg); Iceberg when partition evolution over the table's life, many engines writing, or one standard across many teams; Hudi for high-frequency record-level upserts (CDC replication); Delta is simpler for single-machine / small lakehouse work (polars `deltalake`). The formats are converging; the difference lives in the write path, the catalog and operations.
- **Hidden costs, always shown:** compaction (small files), snapshot expiry / VACUUM (unbounded storage, planning slows), orphan-file cleanup, catalog becomes a hard runtime dependency (Iceberg), vacuum windows vs long-running readers, UniForm is one-directional, over-partitioning (Delta) vs forgetting partition transforms (Iceberg). Adopting Parquet into Iceberg / Delta is metadata-only, but adoption is not compaction.
- CDC landing: JSON is fine for transfer and raw landing; serialise to a table format for schema drift and downstream use; if data already flows through Kafka, reading the topic directly can remove an intermediate storage hop (within retention).

## 3. Modelling (does not go out of fashion)
- Kimball star schema, facts + conformed dimensions, remain the way to express business measures; medallion is a *process* for building them, not a model; ELT vs ETL is where the T runs.
- **Silver preserves what happened in the source; Gold decides what it means analytically** (Type 1 vs Type 2 attributes, surrogate keys, effective dating).

## 4. SCD decisions (each one is a decision point with sub-decisions)
Type 1 overwrite (current state only) · Type 2 new row per change (full history, as-was analysis) · Type 3 previous value column (limited history). Type 2 design questions: surrogate key generation (identity values are unique, not sequential; never order by key) · inclusive vs exclusive EndDate (pick one, document it) · change detection by hash with unambiguous serialisation (NULL token, delimiter, case/whitespace normalisation) · change grain (date vs timestamp, same-day changes) · source-key uniqueness validated before loading · Type 1 attributes inside a Type 2 dimension (excluded from hash, overwritten across versions) · snapshot vs delta feed (closing "missing" keys only on full snapshots) · idempotent retries · validation queries (one current row per key, no gaps/overlaps) because lakehouse/warehouse engines do not enforce uniqueness · fact load joins on the event date range (as-was) — joining on IsCurrent silently gives as-is · unknown member / early StartDate · row growth when an attribute flips often (consider an event fact or mini-dimension). Platform realisations differ: T-SQL two statements in one transaction (a single MERGE cannot close and insert for one source row); Delta MERGE with the union / null-merge-key trick; Fabric Copy Job CDC SCD2 (preview) as a historised landing, not the final dimension; Dataflow Gen2 pattern rebuilds the table (small dimensions, low-code teams).

## 5. Spark performance reasoning
Skew first (one task much slower than the others; salting, repartition, AQE); filter and project before shuffles and joins; broadcast small tables; partition sizing (~128–256 MB per partition as a rough starting point → cores → workers → memory); avoid Python UDFs (use built-ins or Arrow); cache only when reused and measure (cache can slow jobs); table statistics for the cost-based optimiser; read the query plan; small files and file layout (partitioning, Z-order / liquid clustering) often matter more than the format. And the upstream question: is Spark needed at all for this volume (polars / DuckDB on one node, SQL in the warehouse)?
