# Microsoft employee feedback: Fabric notebooks vs Spark job definitions (source digest, PM 18, 2026-09-30)

Source: r/MicrosoftFabric thread "We built a full local dev environment for Microsoft Fabric notebooks" (about 6 months old), brought by Julian. It is summarised and critiqued by the PM, not transcribed. Status: **archived for the catalogue, no change before V1** (Julian's decision). Target: the arch-catalog "practices" family and future arch-lint detectors (backlog CATMS1).

## What the thread teaches (with how much weight each point deserves)

| # | Insight | Who says it | Weight | Catalogue home |
|---|---|---|---|---|
| 1 | Fabric **workspace Git sync** doesn't treat `notebook-content.py` as the whole truth: the item also has metadata (`.platform`, logical ids, workspace state). Edits made outside Fabric can be reverted on "Update" and show up as conflicts. For code produced outside Fabric, **deploy** (the `fabric-cicd` library, or the Git REST `updateFromGit` with a conflict policy) instead of syncing. | Microsoft employee on the Fabric CI/CD side, and the original poster confirmed it works | High (a product owner, confirmed in practice) | practices: deployment; `py.fabric-cicd` is already in the toolkit baseline |
| 2 | **Production Spark code should be a tested package (wheel) run by a Spark job definition (SJD).** Notebooks are for exploration with a human in the loop. A thin notebook that imports the wheel is an acceptable middle ground. | Microsoft employee (Spark user at petabyte scale, strong opinion); a second practitioner agrees | Medium-high. It's an opinion, and others say notebooks have their place. The wheel adds ~3 min to cluster start. | practices: code packaging; platform: Fabric Spark |
| 3 | History: the REPL/notebook style came from Jupyter/Kaggle. Databricks brought notebooks to production around 2017 and now pushes **declarative pipelines with a client-side dry run** (Spark Declarative Pipelines). Lesson: fail before merge, not at runtime. | Same employee | Medium (a narrative, but it matches where Spark and Databricks are heading) | practices: "fail client-side" principle |
| 4 | Pinned Spark runtimes make large notebook estates expensive to upgrade: notebook code breaks at runtime on every Spark upgrade. | Same employee | Medium | practices: upgrade risk (a scale-dependent cost) |
| 5 | Parallelism without notebooks: a driver thread pool (or Scala futures) in an SJD, with `spark.scheduler.mode=FAIR` if needed, instead of `notebookutils.runMultiple`. Whether runMultiple isolates sessions was left unresolved. | Same employee and a practitioner | Medium (partly unresolved) | flows: orchestration inside a job |
| 6 | Local development: a single-node Spark devcontainer or venv pinned to the Fabric runtime version (PySpark 3.5.x, Delta 3.2.x). Behind one abstraction, a shim for `notebookutils`/`mssparkutils` secrets, paths and `%run`. Write locally, read OneLake. | The original poster and the employee | Medium-high (it works in daily use) | practices: local dev parity |
| 7 | Pitfall: renaming or deleting a notebook on the repo side can leave the workspace metadata out of step. Resolve with an Update first, then commit. | Practitioner | Low-medium (anecdotal) | practices: Fabric Git pitfalls |

## DataPass impact (PM verdict)
- **Small, not structural.** DataPass reads native files and never deploys, so the Git sync pitfall is advice for the client guide, not a DataPass bug.
- **Spark job definitions:** the catalogue already names them as a Fabric service (flows, platform, storage entries). The coverage registry lists `*.SparkJobDefinition/**` as **planned** (never extracted). Wave 3 **FABITEM1** (assigned 30 Sept) extracts them: main file → code edge, libraries/Environment as config. So SJDs were known but not understood yet, and FABITEM1 closes that gap. Wheels (`*.whl`, `setup.py`/`pyproject.toml` packages) should get a coverage-registry row in COVREG2.
- **Later (CATMS1, after V1, ~10 M):** catalogue entries 1–7 with sources, plus 2–3 arch-lint detectors: "production notebook chain with shared code through `%run` → suggest a wheel + SJD"; "externally generated Fabric items synced by workspace Git → suggest fabric-cicd deploy"; "no dry-run/test gate before merge on Spark code".

**PM verdict on the addendum:** there's no architecture change. The one real gap is SDP / Lakeflow declarative pipelines as a first-class file family: a pipeline definition whose DAG is implicit in decorators. Backlog **SDP1** (Common, ~12 M, V2): a registry row + extractor (spec → libraries; `@dp/@dlt` and `CREATE STREAMING TABLE / MATERIALIZED VIEW / FLOW` → dataset nodes and edges; sinks as external targets). Everything else is catalogue content for CATMS1.
